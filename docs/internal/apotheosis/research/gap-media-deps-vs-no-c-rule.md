# Gap: media dependencies vs the "no C compiled" rule

Date of research: 2026-11-12. Method: shallow clones under `/home/risk/.cache/apotheosis-prior-art/` (rav1d, cros-libva, cros-codecs, pipewire-rs, pipewire-native-rs, pulseaudio-rs, libva-mlm), crates.io API for licences and versions, extracted crate tarballs for gbm-sys, vk-mem and gpu-video, and vendor docs. Nothing was built or run. Prior-art rule observed: techniques are described in prose.

## Summary

The media dossier (`topic-media.md`) understated the problem in one place and missed a better option in two.

1. rav1d: x86_64 `asm` needs the external `nasm` assembler, and `build.rs` also calls the `cc` crate (on x86_64 only to archive the objects, on aarch64 to assemble `.S` files with the C driver). No C source is compiled. With default features off it is a pure-Rust build. Rust-only decode speed is unverified.
2. cros-libva 0.0.13: runs bindgen against the host's libva headers (needs libclang), but compiles no C. It links `va` and `va-drm` at link time. Committed pre-generated bindings remove libclang from the build.
3. cros-codecs 0.0.6: the `backend` feature unconditionally pulls `gbm` and `gbm-sys`. gbm-sys ships pre-generated bindings and compiles no C, but declares `#[link(name = "gbm")]`, so libgbm becomes a link-time dependency. gbm is used in exactly one file (`src/video_frame/gbm_video_frame.rs`). Another `VideoFrame` implementation (`GenericDmaVideoFrame`) does not use it. A fork can drop gbm with a small patch.
4. pipewire-rs 0.10.1 is worse than the dossier says. `libspa-sys/build.rs` runs bindgen with `wrap_static_fns`, which emits C that is then compiled by `cc`. It also compiles four of its own `.c` files. Pre-generated bindings cannot remove that. Its licence is MIT (never recorded in the dossier).
5. The newer `pipewire-native` 0.2.0 (MIT, freedesktop.org) is a Rust reimplementation of the client library. It does not help: `spa/build.rs` compiles `log.c` and `system.c` with `cc`, and its README says sending and receiving audio/video is not implemented yet.
6. Best audio answer: the `pulseaudio` crate 0.3.2 (MIT, pure Rust, no `build.rs`, no C) speaks the PulseAudio native protocol over a Unix socket. PipeWire serves that protocol through its `pipewire-pulse` module. It exposes playback timing (`GetPlaybackLatency`). No libpipewire, no bindgen, no clang.
7. New finding: young pure-Rust software decoders exist for H.264 (`rust_h264` 0.6.1) and H.265 (`rust_h265` 0.4.1), both MIT OR Apache-2.0. They are single-maintainer and a few months old, so they belong behind the sandbox. VP9 has no pure-Rust option.
8. Vulkan Video through `gpu-video` 0.5.0 (MIT, wgpu 30) is H.264 decode only today and pulls `vk-mem`, which compiles the C++ VulkanMemoryAllocator through `cc`. It is not usable under the rule as it stands.

Recommendation, one option per component:

| Component | Recommendation | Rule or list change needed |
|---|---|---|
| AV1 software | `rav1d` with `asm` on x86_64 only (nasm), pure-Rust fallback elsewhere, inside the sandboxed helper crate only | Rule amendment A below (assembler exception) |
| H.264/H.265 software | Optional `rust_h264` / `rust_h265` in the helper, after a fuzz and conformance pass. VP9 is hardware-only | None |
| VA-API decode | Vendored fork of `cros-libva` + `cros-codecs`: bindings generated by a dev-only xtask and committed, gbm removed. Link `libva` and `libva-drm` | Add `libva-drm` to the list (ships with libva; pulls libdrm transitively) |
| Vulkan Video | Defer. Revisit when gpu-video swaps `vk-mem` for a pure-Rust allocator and adds AV1/H.265 decode | None now |
| Audio output | `pulseaudio` crate to PipeWire's pulse socket. Later: in-tree PipeWire native client | Wording change B below ("PipeWire" means its PulseAudio-protocol module) |

Proposed rule text. Replace "No C/C++ compiled by our build" with:

> A. No C, C++ or Objective-C source is compiled by our build. That includes `.c` files, `.S` files assembled through a C driver, and C emitted by bindgen (`wrap_static_fns`). Bindings are generated by a dev-only xtask and committed, so neither bindgen nor libclang runs in CI or packaging. One named exception: `nasm` may assemble rav1d's x86_64 `.asm` sources in the media-helper crate (ADR required; the `av1-asm` cargo feature is on in packaging and off for dev builds).
> B. The allowed-library list gains `libva-drm` (part of the libva package). PipeWire audio is reached through its PulseAudio-protocol socket (`pipewire-pulse`), with no linked PipeWire library.

Caveat to put in that ADR: rustc invokes the system `cc` as the linker driver, so a C compiler driver is on every Rust build host regardless. The rule is about source we compile, not about the host having `cc`. (rustc book on linkers; not re-verified here.)

## Architecture (how it is built)

### rav1d (BSD-2-Clause)

- Repo HEAD `2e7216c` (2026-10-27) is version 1.1.1; crates.io latest is 1.1.0 (2025-05-07). Licence field: `BSD-2-Clause`.
- `Cargo.toml` features: `asm` (default), `asm_arm64_dotprod`, `asm_arm64_i8mm`, `asm_arm64_sve2` (all imply `asm`), `bitdepth_8`, `bitdepth_16`. Build dependencies: `cc` 1.x and `nasm-rs` 0.3 (feature `parallel`; `nasm-rs` is MIT OR Apache-2.0). Runtime dependencies are plain crates (`libc`, `parking_lot`, `zerocopy`, `av-data`, and so on).
- `build.rs` is entirely behind `#[cfg(feature = "asm")]` (function `asm::main`). With the feature off, `build.rs` does nothing and the Rust fallback routines are used. The README documents `--no-default-features --features bitdepth_8,bitdepth_16` as the no-asm build, "useful when testing the Rust fallback functions".
- With `asm` on, the script writes a generated config header, then:
  - x86 and x86_64: assembles `src/x86/*.asm` with `nasm_rs::Build` (minimum nasm 2.14), then uses `cc::Build` only to archive the objects ("cc is better at finding the correct archiver").
  - arm and aarch64: `cc::Build` compiles `src/arm/**/*.S` with the C compiler driver (with `-march=armv8.6-a[+sve2]` flags on arm64). This is the part that violates "no C compiler".
- The library offers a Rust API in `src/rust_api.rs` (`Settings`, `Decoder::send_data`, `get_picture`, `Picture::plane`) alongside the C ABI.
- Speed: published figures are with assembly on (see Performance). No figure for the Rust-only path was found: unverified.
- Rust-only AV1 alternative: `rav1d-safe` 0.6.0 is AGPL-3.0-only OR a commercial licence. Excluded by the licence list.

### cros-libva (BSD-3-Clause)

- Upstream `lib/Cargo.toml`: version 0.0.13, features `intel-protected-content-headers` only. Build dependencies: `bindgen` 0.70.1, `pkg-config`, `regex`. Runtime: `thiserror`, `bitflags`, `log`.
- `lib/build.rs` `main`: locates libva headers by env `CROS_LIBVA_H_PATH` or `pkg-config libva`, parses `va/va_version.h` (`get_va_version`) and emits `cfg(libva_1_16_or_higher ... libva_1_23_or_higher)`, prints `cargo:rustc-link-lib=dylib=va` and `dylib=va-drm`, then runs bindgen over `libva-wrapper.h` (includes `va.h`, `va_drm.h`, `va_drmcommon.h`). No C is compiled. libclang is needed at build time only.
- `lib/bindgen_gen.rs` `vaapi_gen_builder` allow-lists `va.*` functions and types matching MPEG2, VP8, VP9, H264, HEVC, JPEG, AV1, PRIME and a few more.
- API surface actually called: 35 libva functions (`vaInitialize`, `vaGetDisplayDRM`, `vaCreateConfig`, `vaCreateContext`, `vaCreateSurfaces`, `vaCreateBuffer`, `vaBeginPicture`, `vaRenderPicture`, `vaEndPicture`, `vaSyncSurface`, `vaExportSurfaceHandle`, `vaDeriveImage`, `vaGetImage`, `vaMapBuffer`, and so on). Decode needs about 20 of them. Total crate size is about 8,000 lines.
- A third-party fork named `libva` 0.1.5 (BSD-3, single author `mlm-games`, about 1,450 downloads) adds a `dlopen` feature (libloading) and vendored headers, but still has bindgen as a build dependency. Not a supported option: unverified maturity, no committed bindings.

### cros-codecs (BSD-3-Clause)

- Upstream `Cargo.toml`: crates.io latest 0.0.6 (2025-06-18). The repo HEAD `a050c6c` (2026-10-21) still says version 0.0.5; the mismatch is unexplained (unverified which is newer in content). Features: `backend` (= anyhow, byteorder, thiserror, crc32fast, nix, **gbm, gbm-sys**, drm, drm-fourcc, zerocopy), `vaapi` (= libva + backend), `v4l2`.
- Without `backend`, only `bitstream_utils` and `codec` compile: pure-Rust bitstream parsers and DPB helpers for H.264, H.265, VP8, VP9, AV1 with `log` as the sole dependency. The stateless decoders (`src/decoder/stateless/{h264,h265,vp8,vp9,av1}.rs`, about 4,000 lines) and the VA-API backend (`src/backend/vaapi/decoder.rs`, 331 lines) are behind `backend`.
- gbm touches only `src/video_frame/gbm_video_frame.rs` (784 lines) and the example and C2-wrapper code. The decoder is generic over the `VideoFrame` trait (`src/video_frame.rs`). `GenericDmaVideoFrame` (`generic_dma_video_frame.rs`) is a second implementation with no gbm dependency.
- `gbm-sys` 0.4.0 (MIT): `build.rs` is empty unless the `use_bindgen` feature is on, so it uses pre-generated bindings and compiles nothing. But `src/lib.rs` declares `#[link(name = "gbm")]`, a link-time libgbm dependency. libgbm is not on the allowed list.
- `drm` / `drm-ffi` / `drm-sys` 0.8.1 use `linux-raw-sys` ioctls and need no libdrm for the default build (bindgen is optional, off by default).

### pipewire-rs (MIT)

- Workspace version 0.10.1 (HEAD of `pipewire-rs`, crates.io 2026-08-19); licence `MIT` in workspace `Cargo.toml`. README line: "These bindings are work-in-progress. Expect frequent breakage, bugs and missing features." and lists Clang as a requirement.
- `libspa-sys/build.rs` `main`: `system_deps` probes `libspa-0.2` and `libpipewire-0.3`; bindgen (features `experimental`, `runtime`) with `.clang_macro_fallback()` and `.wrap_static_fns(true)`; then `cc::Build` compiles `src/type-info.c`, `src/command.c`, `src/node-command.c`, `src/meta.c` plus the generated `static_fns.c`. `pipewire-sys` adds bindgen + `links = "pipewire-0.3"`.
- Consequence: this crate needs libclang AND a C compiler AND libpipewire/libspa headers. Pre-generated bindings cannot fix it because the C wrappers for SPA's `static inline` functions must be compiled. Verdict: incompatible with the rule.

### pipewire-native (MIT) and the native protocol

- `pipewire-native` 0.2.0 (2026-09-30, repo `pipewire-native-rs` on freedesktop.org gitlab). README: native implementation of the client library in Rust; "support for connecting to a PipeWire server, enumerating objects, and creating server-side objects is supported. Further work is required for sending and receiving audio/video." Code layout has no stream module (`pipewire/src/proxy/` has node, port, link, registry and others).
- `spa/Cargo.toml`: `libloading` 0.9 (ISC), `cc` build dependency. `spa/build.rs` compiles `src/support/ffi/log.c` and `system.c` (C shims) and the SPA plugins are loaded at run time from the system plugin directory (`pkg-config libspa-0.2 plugindir`). So it violates the rule today and cannot play audio today.
- Protocol facts (docs.pipewire.org native protocol page): socket `pipewire-0` in `XDG_RUNTIME_DIR`; 16-byte header of four u32 words (id, opcode+size, seq, n_fds); payload is one SPA POD. Playback is done by creating a ClientNode via `Core::CreateObject` with the client-node factory, then Update, AddMem, SetActivation, Transport, SetIO, SetActive, PortUpdate, PortUseBuffers; memfds and eventfds travel as ancillary fds. The page states the activation record "is currently an internal data structure that is not yet ABI stable". Writing our own client means POD serialisation, the ClientNode state machine, memfd buffers and eventfd wakeups, and tracking an ABI the project calls unstable. Estimated at several thousand lines (my estimate, not from a source).

### pulseaudio crate (MIT)

- `pulseaudio` 0.3.2 (2026-10-16), repo `colinmarc/pulseaudio-rs`, `Cargo.toml` licence `MIT`, edition 2024. No `build.rs`. Dependencies: bitflags, byteorder, enum-primitive-derive, futures, log, mio, num-traits, thiserror. About 13,000 lines including tests.
- Implements the wire format ("tagstructs") and an async-friendly client: playback stream, record stream, `timing_info` (`src/client/playback_stream.rs`, command `GetPlaybackLatency`), `cork`, `uncork`, `drain`, `flush`. README lists as not implemented: `memfd`/`shm` zero-copy streaming. Audio therefore travels over the socket, which is fine for stereo PCM.
- `PlaybackLatency` fields (`src/protocol/command/timing_info.rs`): `sink_usec`, `source_usec`, `playing`, `local_time`, `remote_time`, `write_offset`, `read_offset`, underrun counter. That is enough to compute the played position for audio-master A/V sync.
- Server side: PipeWire's `libpipewire-module-protocol-pulse` is "a complete PulseAudio server on top of PipeWire", usually run as `pipewire-pulse`. Defaults per docs: `pulse.default.req` 20 ms, `pulse.default.tlength` 2 s, `pulse.min.req`, `pulse.min.quantum`, `pulse.idle.timeout`. Whether major distros enable it by default is not stated on that page: unverified.

### gpu-video / Vulkan Video

- `gpu-video` 0.5.0 (2026-11-10, MIT, repo `software-mansion/smelter`; the earlier `vk-video` crate is deprecated and renamed). README: H.264 decode and encode supported; H.265 encode only; AV1 decode not supported (encode in progress). Decoded frames are `VideoTexture` NV12 wgpu textures kept in GPU memory. Depends on `wgpu` 30, `ash` 0.38, `h264-reader`, and `vk-mem` 0.4 on Linux.
- `vk-mem` 0.4.0 (MIT/Apache-2.0) `build.rs` uses `cc::Build` to compile `wrapper.cpp` against the vendored VulkanMemoryAllocator C++ headers. That is compiled C++ and violates the rule. wgpu-hal itself uses `gpu-allocator`, which is pure Rust, so a swap is plausible but is our fork work.
- `wgpu-hal` (checked 27.0.4 source) has no video decode API. `ash` 0.38 has the Vulkan Video AV1 decode structures (`VIDEO_DECODE_AV1_*`), so a hand-written path is possible but large.
- Driver support for `VK_KHR_video_decode_av1`: RADV since Mesa 24.1 and NVIDIA proprietary; Intel ANV status unclear (Phoronix and Mesa MR results, 2023-2024; may be stale).

## Feature inventory (grouped by category)

Media (decode, container and audio mechanisms, with the verdict per component):

- Software AV1: rav1d. Hand-tuned asm gives near-dav1d speed; needs nasm (x86_64) or `cc` (aarch64).
- Software H.264: `rust_h264` (Baseline/Main/High/High 10/High 4:2:2, MBAFF and field pictures; no FMO/ASO/SP/SI; 199 of 204 JVT conformance vectors pass, the same count as FFmpeg; SSE2/SSSE3/AVX2/NEON motion compensation; `ThreadedDecoder`; MSRV 1.89).
- Software H.265: `rust_h265` (Main, Main 10, range extensions 4:2:0 and 4:4:4 up to 12-bit; 147/147 HEVC_v1 vectors; no hand SIMD; unsafe confined to `src/shared.rs`).
- Hardware: VA-API via cros-libva/cros-codecs for H.264, H.265, VP8, VP9, AV1 (stateless decoder, you parse bitstream and fill VA parameter buffers).
- Frame hand-off: `vaGetImage` or `vaDeriveImage` to NV12 in shared memory (simple), or `vaExportSurfaceHandle` to a DMA-BUF imported into Vulkan (zero-copy; recipe unverified).
- Audio: PulseAudio-protocol client to `pipewire-pulse`, with `timing_info` for the clock.

Packaging and build: see rows under categories `packaging` and `security`.

## Control surface (config, actions, IPC)

Build-time controls (cargo features, not user config):

- `av1-asm` (helper crate feature forwarding to rav1d `asm`), default on in packaging, off in dev.
- `sw-h264`, `sw-h265` (enable pure-Rust decoders).
- `vaapi` (enable the vendored VA-API backend).

Runtime config (KDL, extends `topic-media.md`): `media { hwdec "auto"; av1-software true; sw-codecs "h264" "h265"; audio-output "pulse"; sync-master "audio" }`. Actions: `media-pause`, `media-seek`, `media-set-hwdec`. IPC: a `media.caps` query that reports which decoders are compiled in and which hardware profiles the VA driver reports, so the settings GUI can grey out unavailable options. The helper reports failures back as typed errors (missing libva, missing render node, no pulse socket) for the GUI.

## Performance (numbers + method)

- rav1d vs dav1d, both with assembly: "under 6%" slower on x86_64; initial c2rust port 3.8% slower with all asm enabled, about 7% more instructions, bounds checks about 2%. Rust code is about half of decode time even with all asm. Method: hyperfine on the dav1d CLI, Chimera 8-bit 1080p, 8 threads, Ryzen 7700X. Source: memorysafety.org blog (also quoted in `topic-media.md`).
- rav1d without assembly: no published number found. Unverified. The decision to keep asm in the helper rests on the generic fact that dav1d's per-routine C fallbacks are slower than asm; the size of the gap for rav1d's Rust fallback needs measuring on our hardware (add a bench task, do not rely on guesses).
- `rust_h265` vs FFmpeg: single-thread about 1.5-1.6x slower on 8-bit, about 1.3-1.5x faster on 10-bit; 4 threads give 2.5-3.8x on 1080p fixtures. Hardware not named. Source: repo README.
- `rust_h264`: README gives no fps; `BENCHMARK.md` is referenced but was not retrievable (HTTP 404 at the paths tried). Unverified.
- `pipewire-pulse` buffering defaults: request 20 ms, target length 2 s (docs). Latency to compute for A/V sync comes from `GetPlaybackLatency`; no end-to-end figure found.

## What Apotheosis should take

1. A single, precise amendment (A and B above) instead of per-crate exceptions.
2. rav1d with `asm` on x86_64 as the only assembler exception; Rust fallback on aarch64 and when `av1-asm` is off.
3. Vendored fork of cros-libva + cros-codecs: committed bindings from a dev-only xtask pinned to a libva release at or above the oldest we support (the dossier says 1.20), `cfg(libva_*)` flags set by hand in the vendored `build.rs`, gbm gated out. Keep BSD-3 notices.
4. bindgen's `dynamic_library_name` option (generates a struct loaded through libloading) as an improvement later so a missing libva does not stop the helper starting. From bindgen docs; unverified here.
5. `pulseaudio` crate for audio, behind a small `AudioSink` trait, so an in-tree PipeWire native client can replace it if `pipewire-native` gains streams without C.
6. Pure-Rust software H.264/H.265 as optional features in the sandboxed helper only. Fuzz them in CI before enabling by default.
7. A capability probe so the GUI shows what each build and machine supports.

## What it should avoid

- `pipewire`/`libspa` crates: C compiled, libclang, libpipewire headers, README warns of breakage.
- `pipewire-native` for now: C shims, no stream support.
- `gpu-video` as-is: C++ via `vk-mem`, H.264 only.
- `rav1d-safe`: AGPL.
- `cros-codecs` `backend` feature unmodified: forces libgbm.
- `libva` (mlm-games fork) 0.1.x: still runs bindgen; single maintainer.
- `ffmpeg-next` (WTFPL, wraps C FFmpeg) and `openh264` (C++): violate the rule.
- Writing our own PipeWire native client now: unstable activation ABI and thousands of lines for no user-visible gain over the pulse socket.
- Assuming `pipewire-pulse` is present: the audio sink must degrade to "no audio" with a clear error, not fail the video.

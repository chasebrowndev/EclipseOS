## automation

| ID | Feature | Mechanism we adopt | Control surface | Adopt | Seen in | Rationale |
|---|---|---|---|---|---|---|
| AUTOMATION-01 | One typed Action vocabulary and single dispatcher | One serde-style Action enum with typed, parse-validated arguments; a single dispatch entry point serves keybinds, mouse binds, palette, tab-bar clicks, rules, profiles, layouts, socket and CLI. Socket verbs and CLI subcommands are generated from the Action definition. | KDL `action` nodes; palette; `apo action <name> args`; JSON socket `action.run` | must | wezterm, ghostty, windows-terminal, zellij, tmux, kitty, topic-mux-remote | Every mature multiplexer converges here. zellij's parallel hand-maintained clap enum is the trap; generating the CLI avoids drift. kitty's `action` command (runs any mapped action) is the model for socket parity. |
| AUTOMATION-02 | Stable action IDs, layered override | Each binding or command refers to a stable string ID; user IDs namespaced `User.*`; later config layers override by ID; a null/removed entry deletes a default. Keys, palette entries and menus reference IDs, not copies. | KDL `action id="..."`, `bind key=... id=...`; `unbind` | must | windows-terminal, topic-config-automation, ghostty | Windows Terminal's id model gives clean layered overrides and lets the settings GUI edit by identity. Ghostty's positional chain/unbind is order-fragile by comparison. |
| AUTOMATION-03 | Named macros (action sequences) | An ordered action list in KDL, usable as one action anywhere; a named `macro` can be defined once and referenced by ID. Flags of the trigger apply to each step. Prefer an explicit list over ghostty's append-to-previous-binding `chain=` form because it round-trips through a GUI. | `macro` node; `do { a; b; c }` | must | ghostty (chain), windows-terminal (multipleActions), kitty (combine) | Replaces most Lua/Python glue with no scripting. |
| AUTOMATION-04 | Raw input actions | `send-text` (string escapes), `send-bytes` (raw, bypasses encoder), `send-keys` (symbolic, goes through the key encoder and respects current modes), `csi`, `esc`; plus `ignore` (consume) and `unbind`. | Actions `send-text`, `send-bytes`, `send-keys`, `csi`, `esc`, `ignore` | must | ghostty, wezterm, kitty, foot, windows-terminal (sendInput) | Primitive for binding keys to program input. Keeping the encoder-aware and raw variants distinct avoids wrong output under kitty keyboard protocol or application cursor mode. |
| AUTOMATION-05 | Bindings consume press and release | Binding match runs before the encoder; a matched press and its release are swallowed so apps never see half a shortcut. | KDL `bind` | must | wezterm | Correctness requirement for the keyboard path. |
| AUTOMATION-06 | Key tables, chords, leader and mode conditions | Modal binding tables pushed and popped by Actions; multi-key sequences and a leader key; bindings may carry mode conditions (app cursor, vi, search, alt-screen, and negations). | Actions `key-table.push`/`pop`; `bind ... when="..."` | should | wezterm, ghostty, alacritty, tmux | Large keybind space without modifier clashes; mode conditions cover app-vs-terminal conflicts. |
| AUTOMATION-07 | Palette generated from the action registry | Command = Action + title + description; every command is bindable; palette lists all registry entries with current shortcuts, fuzzy-matched, plus user `command` entries. Never hand-built. | `command` nodes; Action `palette.toggle` | must | ghostty, rio, windows-terminal, wezterm | Matches the one-vocabulary decision. Showing live shortcuts in rows is the discoverability win (rio, WT). |
| AUTOMATION-08 | Pipe text regions to commands | Actions `pipe` with source = visible, scrollback, selection, last-command-output (needs OSC 133), writing to a command's stdin; no shell glue needed. | Action `pipe source=... cmd=...` | must | foot, kitty (launch --stdin-source) | foot's only scripting hook and the basis of fuzzel/xurls workflows; folded with kitty's stdin sources so one verb serves both. |
| AUTOMATION-09 | `launch` action | Creates window, tab, os-window, overlay, split, background process or clipboard-writer with cwd policy (current, home, last-reported), env copy, stdin source, hold-after-exit, split location and bias. | Action `launch type=... cwd=... env=... stdin=... hold=... location=...` | must | kitty, wezterm (spawn), windows-terminal (new-tab/split-pane), zellij | The most reused Action: keybinds, rules, hints, layouts and the CLI all call it. |
| AUTOMATION-10 | Layout-specific verbs through one action | A single `layout` action taking a per-layout verb (resize, mirror, rotate, equalize, maximize, bias cycle) so the vocabulary grows without new top-level actions. | Action `layout verb=... args` | should | kitty, zellij | Keeps the registry flat while supporting several layout engines. |
| AUTOMATION-11 | Declarative layouts and startup | A KDL `layout` document (tree of splits/tabs with launch specs) applied by `ApplyLayout` and by a startup rule; also savable from the live tree via socket. Replaces gui-startup scripting and resurrect-style plugins. | `layout { split ... }`; Action `layout.apply`; `rule on=startup`; socket `layout.save/load` | must | wezterm, zellij, konsole (loadLayout), kitty (sessions) | Most common reason people write Lua in wezterm. |
| AUTOMATION-12 | Rules: event, condition, actions | KDL `rule { on <event>; where <match>; do <actions> }` evaluated by the core on a closed event set. Value-returning hooks (tab title, open-uri handled) use typed templates instead of callbacks. | KDL `rule`; GUI rule editor; socket `rule.list/set` | must | wezterm, iterm2, tmux, kitty, topic-config-automation | The only way to cover event-handler automation without scripting. Closed event set keeps rules serialisable and GUI-editable. |
| AUTOMATION-13 | Closed event set | Events: bell, focus, resize, title-changed, cwd-changed, host/user-changed, prompt-start, command-started, command-finished (exit filter), idle, activity-after-idle, long-running, user-var-changed, osc-notify, osc-progress, colour-scheme-changed, config-reloaded, pane-spawned/exited, open-uri, startup. Escape-sequence parsing raises events (OSC 133 for command events). Each carries named captures usable in templates. | `rule on=...`; socket event stream | must | iterm2 (16 kinds), wezterm, tmux (OSC 133 events), topic-escape-registry | iTerm2's list is the most complete template; tmux shows OSC 133 as the source of command events. |
| AUTOMATION-14 | Long-running command notification | Built-in event after threshold (default 60 s) with command and elapsed captures; action `notify` routes to Abyss/freedesktop notifications. | `rule on=long-running threshold=60s do notify` | must | iterm2 | Top-requested automation; falls out of OSC 133 plus the rule engine. |
| AUTOMATION-15 | Output-match triggers | Linear-time Rust regex (no backtracking) run on completed logical lines, last three wrapped lines, off the render thread; optional instant mode for mid-line; per-process filter; capture substitution (`\0`-`\9`) into action params. Actions: highlight, hyperlink, mark, fold, notify, send-text, run, set title/status/var, stop. | `rule { match regex=... instant=... job=... do ... }` | should | iterm2 | Only iTerm2 ships it, but users rely on it heavily. Rust `regex` lacks lookaround; iTerm2 uses ICU, so imported triggers may need rewriting. |
| AUTOMATION-16 | Coverage-floor action set | Seed the registry from ghostty's ~100 actions (input, clipboard, font size, search, scroll, prompt jump, selection adjust, export, tabs/windows/splits, titles, toggles, reload, undo/redo, quit), foot's ~35, rio's ~60, konsole's D-Bus methods (sendText, copyInputToSessions, monitors, setProfile, resizeSplits) and iTerm2's 30 trigger actions. Any action present in those and absent from ours needs a recorded reason. | `apo action --list` | must | ghostty, foot, rio, konsole, iterm2 | A checklist, not a design. Rows from foot/rio that propose a keybind-only closed enum are rejected as a design (AUTOMATION-30) but are valid as coverage floors. |
| AUTOMATION-17 | User variables via OSC 1337 SetUserVar | `OSC 1337;SetUserVar=name=<base64>` sets a per-pane variable; exposed as `var:` match field, in title templates, and as `user-var-changed` event. | Escape sequence; match field `var`; template `{var.name}` | should | kitty, iterm2, wezterm | Shells feed state into rules and tab titles without scripting. Three terminals ship the same OSC, so it is a de facto standard. Kitty OSC detail unverified. |
| AUTOMATION-18 | Scoped variables | Key-values at pane, tab, workspace, global scope via action and socket; readable in templates and match language. | Actions `var.set`/`var.get scope=...`; `apo var` | should | warp-wave (wsh), iterm2 | Share state between rules and scripts without a scripting language. |
| AUTOMATION-19 | Unified match language | One grammar everywhere (socket targeting, rules, binds, profiles, layouts): `field:regex` joined by and/or/not; fields id, title, pid, cwd, cmdline, env, var, state, neighbor, session, recent; negative IDs count from newest. | KDL `where "..."`; socket `match` param | must | kitty, tmux | One thing to learn and implement; powers targeting everywhere. Kitty grammar chosen as the most complete. |
| AUTOMATION-20 | Stable targeting and env discovery | Opaque stable numeric IDs for panes, tabs, windows plus relative tokens (`last`, `next`, `up-of`, `marked`); `APOTHEOSIS_SOCKET`, `APOTHEOSIS_WINDOW_ID`, `APOTHEOSIS_TAB_ID`, `APOTHEOSIS_PANE_ID` exported into each child so scripts default to their own pane with no lookup. | `target=` on every action and socket verb | must | tmux, zellij, alacritty, warp-wave | Handle IDs cover scripts; tokens cover humans. Alacritty and zellij both export an ID env var and it is the best ergonomics. |
| AUTOMATION-21 | JSON control socket and CLI | Persistent Unix socket (path in env) speaking JSON request/reply with request IDs; CLI subcommands (`apo ls`, `launch`, `send-text`, `get-text`, `set-colors`, `set-title`, `goto-layout`, `reload`, `signal`, `action`) are thin wrappers over the same Actions. Caller identity resolved automatically from env. | `apo ...`; socket methods mirroring Actions | must | wezterm, kitty, warp-wave, konsole, alacritty, tmux | Alacritty's one-shot message per connection is too limited; persistent stream is better. Access gated by Abyss peer credentials. |
| AUTOMATION-22 | Typed event stream with ordered replies | Replies carry request ID and sequence; async notifications are separate lines that never interleave inside a reply; clients subscribe to the same events rules use, so status bars and editors follow state without polling. | socket `subscribe`; JSON lines | must | tmux (control mode guards), topic-mux-remote | wezterm has no subscription; tmux control mode shows the correct framing. Row from topic-config-automation was "should"; upgraded because framing must be in v1 of the protocol. |
| AUTOMATION-23 | Effective-config introspection | `get-config` returns resolved values for a pane/window or global, with overrides applied, as JSON; also pane `get-meta` for properties such as cwd, process, title, user vars. | `apo config get`; `apo pane meta`; socket `config.get`, `pane.meta` | should | alacritty, warp-wave | Scripts and the settings GUI need effective values. |
| AUTOMATION-24 | Textual action syntax shared by CLI and config | `apo do 'action args' ; 'action args'` parses the same syntax as the KDL `do` body and startup actions; `;` chains. | `apo do` | should | windows-terminal, topic-config-automation | One text syntax across CLI, palette input and config. |
| AUTOMATION-25 | Parameterised workflows and snippets | Named command templates with typed placeholders (text, enum, static or command-derived choices) and defaults; inserted into the prompt or run. Snippets are saved `send-text` actions in the palette. | KDL `workflow`; Action `workflow.run name=... args` | should | warp-wave, windows-terminal | Reuses the Action vocabulary. Warp row said must; two shipping terminals justify should, and dynamic enums can follow. |
| AUTOMATION-26 | Coprocess | A sandboxed helper bound to a pane receiving its output and optionally writing input. | Action `coprocess.run`; socket subscribe overlaps | could | iterm2 | Overlaps with socket subscription, which already provides a safer path. Sandbox required. |
| AUTOMATION-27 | Named pipes into panes | `apo pipe` sends payloads to a pane or UI element with back-pressure. | `apo pipe`; socket `pipe` | could | tmux-zellij | Generic keep-it-simple variant of zellij's plugin pipes. |
| AUTOMATION-28 | Condition monitors | A rule condition polled or evaluated on change (format becomes true) rather than on a named event, as tmux monitors do. | `rule on=monitor where=...` | could | tmux | Only tmux ships it; closed event set may suffice. |
| AUTOMATION-29 | Graphics actions and events | Actions `graphics.save-image`, `copy-image`, `open-image`; events `image-received`/`image-denied` with protocol, byte count, medium; policy-gated; never log content. | Actions; `rule on=image-received` | could | topic-graphics | Differentiator; writes files so needs consent prompt. |
| AUTOMATION-30 | Media actions and events | Surface-addressed `media.open/play-pause/seek/rate/volume/mute/track/close`; events `media.started/ended/error/position`. | Actions; socket `media.list/open/control/state` | must | topic-media | Needed for the native media protocol to be scriptable under the one-vocabulary rule. |
| AUTOMATION-31 | Font actions and font query CLI | Actions `font-size-increase/decrease/reset/set`, `ligatures-set scope=...`, `font-feature-toggle`, `font-family-set`, `font-reload`, `font-clear-caches`, `blending-set`; `apo font query/list/metrics` reports resolving face and reason (primary, symbol-map, fallback), cell metrics, baseline, decoration geometry. | Actions; `apo font ...`; socket `font.*` | must | topic-fonts, kitty, ghostty | Removes a class of support questions. |

### Open questions

- Event payload schema: which captures are available per event, and do template expressions need conditionals or only substitution?
- Do `where` regexes use Rust `regex` only (no lookaround)? iTerm2 trigger import would need a translation story.
- Rule evaluation order and loop protection (a rule's action raising an event that retriggers it); stop-processing semantics.
- Socket authorisation: which actions need an Abyss consent prompt when invoked by a pane's own child versus an external client (e.g. send-text into another pane, pipe, coprocess).
- OSC 1337 SetUserVar details for kitty are unverified; confirm and decide whether to accept the kitty form too.
- Whether `apo` mirrors tmux-style session/window/pane target strings or only IDs plus match language.
- Whether condition monitors (AUTOMATION-28) are redundant with a `long-running`/`idle` event plus match.
